# 每日精读视频

把每天的灵修材料制作成风格稳定、可核验的 720×1280 中文竖屏视频。先读取当天材料和已有素材，再按固定结构制作；不得凭记忆改写经文或传道人的原意。

## 先确认输入

读取 `references/input-contract.md`。优先使用用户上传的当天灵修长图、经文范围和真人朗读素材。若用户没有上传真人朗读，不要立即把寻找音源的工作交还用户：先检查上一期项目配置、素材和成片，找出已使用的来源，再从同一来源主动搜索并下载当天章节。只有同源和其他可用真人音源都找不到，或授权状态不清楚时，才向用户说明缺项；任何情况下都不得用合成音冒充真人朗读。

判断“同一音源”时，至少核对译本、朗读者或声线、章节内容与时长；下载成功不等于与上一期同源。若只能找到不同朗读者的新音源，明确说明差异并取得用户同意后再制作。每次把来源名称、来源页面、直接音频地址、译本、书卷章节和原始时长写入 `project.json`，便于下一期直接追溯。

用户已确认 WordProject 中文音频圣经的中文和合本真人男声为本系列固定默认音源。后续章节优先沿用同一站点、同一系列和同一朗读声线，不再每日重新选择来源；只有该章缺失、不可用或授权状态发生变化时，才寻找替代音源并先取得用户同意。

截图 OCR 只能作为文字提取初稿，不能单独作为书卷判断依据。提取后必须交叉核验四项：书卷名、章数、分段节数与标题、正文主题。若其中任何一项不一致，先放大原图重新辨认，并用分段内容反查书卷章节；仍无法确定时再向用户提出一个最小化确认问题。四项未核对一致前，不得开始制作，也不得把未经核验的识别结果告诉用户。

若用户说“按昨天的方法”或“延续上次”，使用本技能的固定规格，不要求用户重新说明已经固化的偏好。只有章节、分段、解释文本或真人音频确实不明确时，才询问一个最小化问题。

## 固定内容结构

先根据传道人原始解释的篇幅和信息密度选择解释模式，不以机械字数阈值判断：

- **分段解释模式（解释较长）**：原文能够在不扩写、不重复、不割裂语义的前提下，为各经文分段各自分配一段内容完整、主题对应的解释。此时沿用逐段结构，在每一段真人经文之后加入该段的“经文解释”。
- **集中解释模式（解释较短）**：原文不足以为每个经文分段各自提供一段有实质内容的解释，或硬拆后会出现重复、牵强对应、残句。此时各段只播放标题和真人经文，不在每段后重复加入“经文解释”；待全部分段经文读完后，只加入一次“经文解释”先导页，并完整朗读原始解释。集中解释不标“第几段”，也不虚构对应节数。
- 临界情况优先选择集中解释模式。不得为了凑齐每段解释而扩写传道人的话、重复同一句、改变原意或把一句话任意拆散。

依次制作：

1. 片头先念“每日读经，精读”及当天日期，读完后再开始中文歌诗第一节。片头与片尾歌诗使用同一布局，上方放“每日读经｜精读”、日期、歌名和乐谱，左侧歌词自下而上滚动，右侧竖排当期选用的经文及出处。进入正文后先读书卷与章数，例如“路加福音第十章”。
2. 每一部分开始前设置渐进式先导页，固定顺序为“第几段 → 分段标题 → 节数范围”：上方显示“第一段／第二段／第三段……”；中间居中显示分段标题；下方显示“第几节到第几节”。标题配音也按同一顺序读出。前一部分结束后先保留约 2.0 秒安静停顿，标题读完后再保留约 1.2 秒停顿，才进入真人经文朗读，让听众明确感知新段落开始。不得直接硬切到正文。
3. 进入经文正文后，将同一“节数 + 分段标题”移到上方显示，正文置于中部；不要让上方标题与居中标题同时重复出现。
4. 完整保留该部分真人经文朗读。
5. 使用分段解释模式时，进入该段解释前先用相同的渐进式先导页显示“第几段／经文解释／节数范围”，但标题配音只读“经文解释”，不得朗读“第几段／第几部分”，也不重复朗读节数。前一段经文结束后先保留约 2.0 秒安静停顿，读完“经文解释”后再保留约 1.2 秒停顿，随后播放该段解释的自然普通话合成配音并显示同步字幕。不得只显示解释标题而不朗读。
6. 使用集中解释模式时，先依次完成所有分段标题和真人经文；最后一段经文结束后保留约 2.0 秒安静停顿，再显示一次不带段序和节数的“经文解释”先导页，标题配音只读“经文解释”，读完后保留约 1.2 秒停顿，随后完整播放传道人解释并显示同步字幕。不得在前面各段插入空的、重复的或勉强拆分的解释页。
7. 经文分段及所选解释模式完成后，设置渐进式“全文朗读”先导页，再由真人合并朗读全文。
8. 最后先设置渐进式“祷告应用”先导页，再进入祷告正文。
9. 祷告结束后短暂保留祷告画面，再直接交叉淡入完整中文歌诗。保留乐谱和自下而上滚动的歌词，并同屏显示与当日章节主题相呼应的竖排经文及出处。经文至少停留 8 秒，默认不另配朗读。交接处保持画面连续可见。

## 画面与声音

读取 `references/video-spec.md` 并以 `assets/style-reference.png` 为视觉参考。

- 保持黑色微暖背景、米白经文、柔和暖金讲解文字和细分隔线。
- 可使用贴合当日经文的宗教风格背景图，保留原有上下标题、段序及节数。片头同一首歌的器乐版贯穿正文，读经、讲解和祷告时自动降低伴奏音量。
- 所有文字相对 2026 年 9 月 23 日《路加福音》第 13 章成片统一放大一级，基准约为原字号的 108%；优先减少每屏字数与重新断行，不得为了塞入长句而整体缩回旧字号。
- 经文正文使用中文宋体或其他衬线字体；讲解字幕使用中文黑体或其他无衬线字体。两者保持同等表观字号，但必须通过字体和颜色一眼可辨。
- 解释页底部固定写“经文解释｜普通话配音”。
- 经文保留固定音源的真人男声；讲解和祷告应用使用用户已确认的本地 Qwen3-TTS Base `CC0女声D-柔和讲解`。每句保留自然起音与收音，使用约 25 毫秒淡入淡出和约 0.22 秒句间停顿，避免硬切产生刺啦声；只做响度统一，保持沉稳、自然、有停连的普通话。
- 所有章节分段、经文解释、全文朗读与祷告应用均使用风格一致的渐进式先导页。分段解释模式的解释先导画面保留段序和节数；集中解释模式的解释先导只显示“经文解释”，不显示段序或虚构节数；两种模式的语音都只读“经文解释”。推荐淡入 0.9–1.2 秒并配合轻微上移；段落切换不得短于 0.9 秒，避免突兀跳切或夸张动效。
- 分段先导页的段序、标题和节数必须同时保持清楚可见；段序不得省略，也不得把节数读在标题前面。段落间停顿属于结构提示，不得在后期自动裁掉。
- 字幕必须依据实际生成音频的句界或词界时间戳生成，不能只按总时长平均切分。
- 真人经文朗读保留原声；发现异常长停顿时仅修剪静音，并同步剪切视频和音频，避免后文漂移。

## 制作顺序

1. 从当天材料逐字提取书卷、章数、各分段节数、标题、解释和祷告。建立结构化项目清单，并依据解释能否自然、完整地对应各分段，明确记录采用“分段解释模式”还是“集中解释模式”。
2. 对结构化清单执行书卷名、章数、分段标题和正文主题四项交叉验证，确认彼此一致。
3. 沿用上一期音源记录主动取得当天章节；核对译本、声线、章节内容和时长，确认是同源或已获用户同意的新音源。
4. 检查经文版权与音源授权，并把完整音源信息写入 `project.json`。经文内容不作神学改写；传道人解释只做必要的读音、标点和停连处理。
5. 从真人朗读素材切出各分段和全文朗读；保留自然呼吸，检查断句与长静音。
6. 生成标题、解释和祷告音频。解释使用实际音频边界写 ASS/SRT 字幕。
7. 按固定结构合成画面。需要建立 HTML 视频合成时使用 HyperFrames；已有成片母版或精确片段替换时可使用 ffmpeg。
8. 先抽帧检查标题、正文、解释、全文朗读和祷告五类画面，再做全片音视频解码检查。
9. 保存高清 MP4 母版与当天项目配置。通过成片验收后，继续完成下方的手机发布与线上验收。

## 每日手机发布

常规每日精读交付包含手机网页发布。用户明确要求只做预览、试片或暂缓发布时，按其要求停在相应步骤。

1. **生成手机播放文件。** 从已验收的高清 MP4 生成 540×960 的 HLS（约 6 秒一段、可独立解码），与高清 MP4 一并放入仓库当日的 `videos/YYYY-MM-DD/` 目录，同时准备首页所需的封面和当期项目配置。GitHub Actions 只部署仓库中已有的文件，转码在推送前完成。
2. **更新首页。** 在 `index.html` 把当天日期、书卷章次和播放器放到最新一期位置，原最新一期移入往期。播放器将 HLS 放在 MP4 之前，供 iPhone/iPad 优先原生播放，MP4 作为其他浏览器的后备。提交前检查页面所引用的媒体、封面和 HLS 分段均存在。
3. **推送并等待部署。** 将当期文件与首页更新一并提交、推送到 GitHub 的 `main` 分支，检查该提交对应的 GitHub Pages 工作流，直到部署成功。
4. **验证线上链接并交付。** 打开线上首页确认最新一期的日期、章节和媒体链接正确。确认 HLS 播放列表及首尾分段均返回 HTTP 200，并向 MP4 发出实际字节范围请求确认返回 HTTP 206。验证通过后交付手机播放页和 MP4 直链。如果仍在部署或无法通过验证，说明当前状态和具体卡点。

## 验收门槛

运行 `scripts/qa_video.py <成片.mp4>`。同时人工核对：

- 片头是否先念“每日读经，精读”与正确日期，再进入歌诗。正文第一句是否为正确书卷与章数。
- 书卷名、章数、分段标题和正文主题是否彼此一致。
- 真人朗读是否来自上一期同源，或已经用户明确同意更换；不得仅凭可下载就认定同源。
- `project.json` 是否记录来源页面、直接音频地址、译本、章节和原始时长。
- 每一部分开场是否依次显示并读出“第几段 → 标题 → 节数”；正文阶段上方显示节数和标题。
- 前一部分结束至新段标题配音前是否有约 2.0 秒停顿，标题读完至真人经文开始前是否有约 1.2 秒停顿。
- 是否按原始解释的实际篇幅和信息密度正确选择模式：解释较长且能自然对应各段时采用分段解释；解释较短或无法自然拆分时采用集中解释；不得为凑段落而扩写、重复或牵强拆句。
- 每一部分、经文解释、全文朗读与祷告应用开始前是否都有柔和渐进的先导页，没有直接硬切；分段解释模式的解释先导是否显示段序、标题和节数，集中解释模式是否在全部分段经文之后只出现一次且不显示段序或虚构节数；两种模式的语音是否都只读“经文解释”，且前后停顿完整。
- 经文是否全程为真人朗读，解释是否为自然普通话。
- 经文是否为米白衬线字体，讲解是否为暖金无衬线字体；两者字号相当且视觉上明确区分。
- 经文是否继续使用固定的 WordProject 中文和合本真人男声音源，讲解是否为女声。
- 解释字幕是否逐句跟随声音，没有整体落后或提前。
- 全文朗读页是否只使用“全文朗读”。
- 页脚是否为“经文讲解｜普通话配音”。
- 字体是否与母版一致，正文和解释字幕表观大小一致。
- 全片各级字号是否已在 2026 年 9 月 23 日母版基础上统一放大一级；长句是否通过减少每屏字数和重新断行保持可读，而非缩回旧字号。
- 是否存在不自然停顿、切字、重复段落、黑帧或静音尾巴。
- 片头是否只唱中文歌诗第一节、标题和日期正确，正文同曲器乐伴奏是否可听且不盖住人声。
- 祷告到片尾完整歌诗是否直接交叉淡入，有无空白帧。检查片头与片尾同款布局、乐谱、向上滚动的歌词，以及右侧竖排经文和出处。

若任一项失败，修订对应片段后重新拼接并复检，不要在未完成解码检查时交付。
